# Разрешение зависимостей — nhopkg v1.0

Единая система разрешения зависимостей (UDEPSYS) — это модуль, отвечающий за
разрешение, загрузку и установку зависимостей пакетов. Он реализован в
библиотеке **`libnhopkg_udepsys`** (устанавливается в
`/usr/lib/nhopkg/libnhopkg_udepsys`) и подключается основным исполняемым файлом
`nhopkg`. Модуль предоставляет публичные точки входа `dep_resolve_from_nhoid()`,
`dep_install_queue()` и `dep_check_conflicts()`, а также вспомогательные функции
`version_compare()` (сравнение версий через `sort -V`) и `get_repo_url()`
(построение URL репозитория). Загрузка пакетов делегируется единому
загрузочному бэкенду `nhoget_url` из [`libnhopkg_download`](nhoget.md).

Полный синтаксис полей nhoid (включая поля зависимостей, специфичные для
разделённых пакетов) описан в [формате nhoid](format-nhoid.md).

---

## Типы зависимостей

Поддерживаются четыре типа зависимостей, каждый из которых проверяется на своём этапе:

| Тип | Внутренний ключ | Когда проверяется | Поведение при сбое |
|---|---|---|---|
| `# BuildDep:` | `build` | Перед `nbuild()` | Жёсткий сбой при отсутствии |
| `# OptionalBuildDep:` | `optional_build` | Перед `nbuild()` | Только предупреждение |
| `# Dep(post):` | `required` | Перед `ninstall()` | Жёсткий сбой при отсутствии |
| `# OptionalDep(post):` | `optional` | Перед `ninstall()` | Только предупреждение |

Жёсткие сбои (`required` и `build`) прерывают установку или сборку с ошибкой.
Необязательные типы (`optional` и `optional_build`) выводят предупреждение и
продолжают работу.

## Операторы сравнения версий

Каждая спецификация зависимости может содержать ограничение версии с использованием одного из следующих операторов:

| Оператор | Значение |
|---|---|
| `=` | Равно |
| `!=` | Не равно |
| `<` | Меньше |
| `<=` | Меньше или равно |
| `>` | Больше |
| `>=` | Больше или равно |

Сравнение выполняет `version_compare()`, который делегирует работу `sort -V`
(естественная сортировка версий). Функция сравнивает версию установленного
пакета или пакета из репозитория с ограничением и возвращает успех, если
ограничение удовлетворено.

Примеры:

```
foo>=2.0
bar<1.5
baz!=3.0
qux=1.0
quux>4.0
```

Спецификация без оператора соответствует любой версии.

## Порядок разрешения

При разрешении одной зависимости UDEPSYS выполняет поиск в следующем порядке.
Побеждает первое совпадение.

**УРОВЕНЬ 1 — установленные пакеты (точное имя)**
Сканирует `${ROOT_PKG_STATE_DIR}/packages/` в поисках файла, внутреннее поле
`# Name:` которого совпадает с именем зависимости. Ограничения версии
проверяются относительно установленной версии.

**УРОВЕНЬ 2 — установленные пакеты (Provides)**
Если точного совпадения по имени нет, у каждого установленного пакета
проверяется поле `# Provides:`, соответствующее имени зависимости
(с необязательной версией).

**УРОВЕНЬ 3 — пакеты репозиториев (точное имя)**
Перебирает каждый активный репозиторий (из `$NHOPKG_ACTIVE_REPOS`). Для каждого
репозитория сначала ищется файл с именем, точно совпадающим с зависимостью,
затем файлы, у которых внутреннее поле `# Name:` совпадает. Ограничения версии
проверяются.

**УРОВЕНЬ 4 — пакеты репозиториев (Provides)**
Если ни в одном репозитории нет точного совпадения по имени, вызывается
`resolve_virtual_package()` для поиска по всем пакетам репозиториев строки
`# Provides:`, соответствующей имени зависимости.

### Кэширование

Результаты кэшируются в ассоциативном массиве `DEP_RESOLVED_CACHE` (ключ —
строка спецификации зависимости). Если та же спецификация запрашивается снова
в рамках одной сессии, немедленно возвращается кэшированный результат, и
сканирование репозиториев не выполняется. Имя репозитория хранится отдельно в
`DEP_REPO_CACHE`.

## Provides и Conflicts

### Provides

Пакет может объявить, что он **предоставляет (provides)** виртуальный пакет,
добавив поле `# Provides:` в свой nhoid:

```
# Provides:	sdl2
```

Несколько виртуальных пакетов разделяются пробелами. Предоставления с версией
выражаются с помощью `=`:

```
# Provides:	libfoo=2.0
```

Когда зависимость не удовлетворяется ни одним реальным именем пакета, механизм
разрешения проверяет, не *предоставляет (provides)* ли какой-либо пакет
(установленный или из репозиториев) запрошенное имя (УРОВЕНЬ 2 и УРОВЕНЬ 4 выше).

### Conflicts

Пакет может объявить, что он **конфликтует (conflicts)** с другим пакетом:

```
# Conflicts:	sdl2
```

`dep_check_conflicts()` проверяет, что ни один установленный пакет (или
предоставитель конфликтующего имени) не соответствует ограничению. Если
обнаружен конфликт, операция прерывается с ошибкой.

### Замена (самоконфликт)

Существует особый случай, когда пакет **конфликтует с тем, что он также
предоставляет**. Это означает *замену* — новый пакет предназначен занять
место старого:

```
# Provides:	sdl2
# Conflicts:	sdl2
```

В этом случае механизм разрешения устанавливает `DEP_REPLACE_PACKAGE` в имя
старого пакета, а процедура установки (`_dep_install_single()`) удаляет старый
пакет перед установкой нового.

Ограничения версии работают как с Provides, так и с Conflicts:

```
# Provides:	libfoo>=2.0
# Conflicts:	libfoo<2.0
```

## Зависимости, специфичные для разделённых пакетов

Когда пакет определяет разделённые подпакеты (`# Splitpackage: dev lib docs`),
каждая часть может нести собственные поля зависимостей с суффиксом `_<part>`:

```
# Dep_dev(post):	libfoo-dev
# OptionalDep_lib(post):	lib32-gcc
# BuildDep_lib32:	cmake
```

Суффикс соответствует имени разделённой части, объявленному в `# Splitpackage:`.
Суффикс добавляется к любому из четырёх типов зависимостей:

| Поле | Значение |
|---|---|
| `# Dep_dev(post):` | Обязательная зависимость времени выполнения для подпакета `dev` |
| `# OptionalDep_lib(post):` | Необязательная зависимость времени выполнения для подпакета `lib` |
| `# BuildDep_lib32:` | Обязательная зависимость сборки для подпакета `lib32` |
| `# OptionalBuildDep_docs:` | Необязательная зависимость сборки для подпакета `docs` |

Тот же механизм суффиксов применяется к `# Provides:` и `# Conflicts:`:

```
# Provides_dev:	libfoo-dev
# Conflicts_lib32:	lib32-libfoo
```

## Процесс разрешения

Конвейер разрешения состоит из трёх публичных функций, вызываемых последовательно:

### 1. `dep_resolve_from_nhoid()`

Читает файл nhoid и разрешает все зависимости заданного типа (`required`,
`optional`, `build` или `optional_build`). Для каждой спецификации зависимости,
найденной в соответствующем поле, вызывается `_dep_resolve_single()`.

- Если зависимость required/build не может быть разрешена, функция немедленно
  вызывает `exit 1`.
- Если зависимость optional/optional_build не может быть разрешена, выводится
  предупреждение, и разрешение продолжается.
- Если включено рекурсивное разрешение (по умолчанию), для каждого вновь
  найденного пакета из репозитория вызывается `_dep_resolve_children()`,
  разрешающий его собственные зависимости того же типа.

Пакеты, найденные в репозиториях, добавляются в `RCASEPACKAGES`
(required/build) или `ORCASEPACKAGES` (optional/optional_build).

### 2. `dep_install_queue()`

Устанавливает все пакеты, накопленные в очередях разрешения. Эта функция:

1. Показывает пользователю список пакетов и запрашивает подтверждение
   (если только `ask_user=no`).
2. Вызывает `_dep_download_all()`, которая загружает каждый пакет из его
   репозитория через `nhoget_url` (единый загрузочный бэкенд: GNU wget,
   curl или BusyBox wget).
3. Вызывает `_dep_install_all_from_queue()` (определена в `nhopkg.in`), которая
   устанавливает каждый загруженный пакет через `_dep_install_single()`.

`_dep_install_single()` обрабатывает проверку конфликтов (через
`dep_check_conflicts`), обновления, замены, проверку хэша, проверку
архитектуры, проверку подписи и собственно установку файлов.

### 3. `dep_check_conflicts()`

Проверяет объявления `# Conflicts:` пакета относительно набора установленных
пакетов. Для каждой спецификации конфликта:

1. Проверяет, установлен ли конфликтующий пакет по точному имени.
2. Проверяет, *предоставляет (provides)* ли какой-либо установленный пакет
   конфликтующее имя.
3. Если конфликт обнаружен и пакет также *предоставляет (provides)*
   конфликтующее имя, это считается *заменой* (см. выше), а не ошибкой.
4. Возвращает ненулевой код, если обнаружен неразрешимый конфликт, что
   заставляет вызывающий код прервать операцию.
